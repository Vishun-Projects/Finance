Key decisions

01
WebSocket over HTTP polling
40M GPS pings/min with polling = 40M HTTP requests/min. WebSocket keeps one persistent connection. Server pushes only when data changes. 10× less load.
✗ Polling — 40M req/min, header overhead ✓ WebSocket — push on change only
02
H3 hex grid over PostGIS radius queries
PostGIS scans millions of rows per request — O(n). H3 converts GPS to a hex ID. Finding nearby drivers = Redis hash lookup in O(1). Constant time regardless of driver count.
✗ PostGIS — O(n) table scan ✓ H3 + Redis — O(1) hash lookup
03
Score-based dispatch
Nearest driver first seems obvious. A driver with 30% acceptance rate wastes 70% of offers. Scoring model optimises system-wide efficiency, not just one trip's distance.
✗ Nearest first — offer waste, cascading delays ✓ Scored — system efficiency optimised
04
Kafka for every state change
Direct service calls create tight coupling. If Payment is down, Trip Service fails too. Kafka decouples: emit event, move on. New services subscribe without changing upstream code.
✗ Sync calls — one failure cascades ✓ Kafka — independent, resilient consumers

How it stays fast at scale

01 Stateless services — any instance handles any request +
Every microservice stores zero session data in the process. State lives in Redis or MySQL. This means any instance can handle any request. Under load: spin up 100 more Dispatch Service instances in 30 seconds. AWS Auto Scaling triggers on CPU + queue depth.
02 Circuit breakers — failures don't cascade +
If Payment Service goes down, Trip Service shouldn't crash. Circuit breaker: after 5 consecutive failures, open the circuit — stop calling it, return a fallback. After 30 seconds, try again (half-open). One failing service never takes down the whole system.
03 Read replicas — writes and reads never compete +
MySQL has 1 primary (writes only) and N read replicas. Trip history, analytics, and dashboards all hit replicas — never the primary. Write latency stays predictable even under heavy read traffic. Replication lag is typically <1 second.
04 Multi-region active-active — no single point of failure +
Uber runs in multiple AWS regions simultaneously. Each region handles its own geography. A US-East failure doesn't affect Asia-Pacific. Cassandra's multi-region replication keeps location history consistent. DNS-based failover reroutes within seconds.

How they keep the codebase maintainable

01 Service ownership — "you build it, you run it" +
Amazon's two-pizza team rule: each team owns exactly one service, its database, its on-call rotation, and its SLA. No shared services, no shared databases. If your service goes down at 3am, your team pages. This incentivises writing reliable code, not just fast code. Teams deploy independently — no coordination tax between teams.
02 API contracts — stable interfaces between services +
Services communicate via published API contracts (Protobuf/gRPC schemas or OpenAPI specs). Changing an internal implementation is fine — changing a published API requires a versioning process. Teams iterate internally without breaking consumers. Uber uses Thrift/gRPC; Amazon uses an internal service mesh.
03 Observability — logs, metrics, traces on every request +
Every production request emits: structured logs (what happened), metrics (counts and durations → Prometheus / DataDog), and distributed traces (which services were called with what latency → Jaeger / Zipkin). When something breaks, engineers follow a single request ID through every service it touched in under a minute. Without this, debugging microservices is impossible.
04 Chaos engineering — break things on purpose +
Netflix invented "Chaos Monkey" — randomly terminate production instances to find what breaks. Uber runs "Fitness Functions" testing real failure scenarios (DB failover, service outage, network partition) in production during low-traffic hours. Better to find failures on a Tuesday at 2am than on Diwali at 8pm when 10× traffic hits.
05 Infrastructure as Code — every server is reproducible +
Every EC2 instance, load balancer, Redis cluster, and Kafka topic is defined in Terraform or CloudFormation. No manual server config. Spinning up a new region takes hours not months. Disaster recovery is automated. "Works on staging" is actually true because staging is defined by the same code as production.

06 Dependency updates — automated, weekly +
Dependabot or Renovate opens PRs weekly for dependency updates. Security patches merged same day. Minor version bumps reviewed and merged in the same sprint. Letting deps go stale for 6 months means a 3-day upgrade sprint instead of a 15-minute one. Uber maintains a policy: no dependency more than 2 major versions behind.
07 Idempotent operations — retries never cause duplicates +
Network failures cause retries. Retries cause duplicate operations unless the operation is idempotent (same input = same result, no matter how many times you call it). Amazon's checkout uses idempotency keys on every payment call. Uber uses them on trip creation. Pattern: client generates a UUID request_id, server stores it, rejects duplicates with the original response.
08 Dead letter queues — no job silently fails forever +
Kafka and SQS jobs that fail after N retries are moved to a Dead Letter Queue (DLQ). Engineers get alerted. The job isn't lost — it's parked. Operations team can inspect, fix the data, and replay. Without DLQs, failed jobs either loop forever or vanish silently. Both are worse than a DLQ.
09 Service mesh — observability and security at network level +
Uber uses Envoy sidecar proxy on every pod. All inter-service traffic goes through Envoy, which handles: mTLS (service-to-service encryption), retries, circuit breaking, and emitting trace spans. This gives you observability across every internal call without touching application code. Istio or Linkerd achieves the same in K8s environments.
10 Graceful shutdown — in-flight requests complete before pod dies +
When K8s kills a pod (during rolling deploy), it sends SIGTERM first. The app catches SIGTERM, stops accepting new connections, waits for in-flight requests to finish (up to 30 seconds), then exits cleanly. Without this, ~2% of requests during a deploy get a connection reset error. Configured via terminationGracePeriodSeconds in K8s deployment spec.

The thing between your database and bankruptcy.

Cache invalidation — the hardest problem

"There are only two hard problems in computer science: cache invalidation and naming things." — Phil Karlton

Stale cache data causes worse bugs than no cache at all. A user sees their complaint as "open" for 30 seconds after it was assigned. Small frustration. But stale inventory data causes overselling. Catastrophic.

TTL
Time-to-live — simplest, most common
Set an expiry on every cached key. After TTL, next request gets fresh data. TTL calibrated to how often data changes and how bad stale data is. Live GPS → 5s. Dashboard summary → 60s. Product catalog → 1hr. Config data → 24hr.
✗ Too long TTL — stale data causes user confusion ✓ Calibrated TTL per data type — fresh enough, fast enough
WRITE
Write-through — update cache on every write
When complaint status changes → update PostgreSQL AND update Redis in the same operation. Cache always matches DB. No TTL wait. Used for high-read, frequently-updated data. Extra write cost is worth the read freshness. Uber does this for trip state.
✗ Write to DB only — cache stale until TTL expires ✓ Write-through — cache and DB always in sync
PURGE
Event-driven invalidation — precise, complex
When an entity changes → emit a Kafka event → cache invalidation consumer deletes or updates specific Redis keys. Precise — no unnecessary TTL expiry. Complex — requires a consumer. Amazon uses this for product price changes affecting thousands of cached pages.
✗ Shotgun TTL — all caches expire together, DB spike ✓ Event-driven purge — precise, no thundering herd
HERD
Thundering herd — what happens when cache expires
10,000 users hitting a page. Cache expires. All 10,000 requests simultaneously hit the DB. DB collapses. Solution: cache lock (only one request rebuilds cache, others wait) OR probabilistic early expiry (start refreshing before TTL, not after). Cloudflare calls this "stale-while-revalidate".
✗ Naive TTL — thundering herd on expiry ✓ Lock + early refresh — smooth DB load

Idempotency — the law of payment systems

A network timeout on a payment request leaves you in a nightmare: did the payment go through or not?

When an entire datacenter burns down. And users notice nothing.

Why single-region fails

Any single datacenter will fail. The question is not if — it is when and are you ready.

Three DR architectures — in order of cost and resilience

Tier 1

Backup and restore — cheapest, slowest

Daily DB backups to S3. On failure: restore backup, restart app. RTO: 1–4 hours. RPO: up to 24 hours of data loss. Acceptable for internal tools, non-critical systems. Not acceptable for anything customer-facing. This is what most startups actually have, even if they don't know it.

Daily S3 backupRTO: 1–4 hoursRPO: up to 24h data loss
Tier 2

Warm standby — second region, reduced capacity

Secondary region runs with 25% of production capacity. DB continuously replicated via streaming replication (async). On failure: promote secondary DB to primary, scale up instances, redirect DNS. RTO: 15–30 minutes. RPO: seconds. Swiggy and Blinkit operate here. Cost: ~40% extra infra spend.

Streaming replication25% capacity standbyRTO: 15–30 minRPO: seconds
Tier 3

Active-active — traffic in both regions simultaneously

Both regions serve real production traffic all the time. DB synchronised bidirectionally (CockroachDB or Aurora Global). On failure: failed region's traffic instantly routed to healthy region via DNS/anycast. RTO: under 60 seconds. RPO: near zero. Used by Uber, Amazon. Cost: 2× infra. Required when downtime directly costs money every second.

10 things to never do — lessons from all five companies

01

Never trust client timestamps

created_at, updated_at, closed_at — always set server-side. Client clocks are wrong, manipulable, and timezone-inconsistent. PostgreSQL DEFAULT NOW() on every timestamp column.

02

Never query in a loop

N+1 is how Swiggy's DB caught fire at scale. Fetch all IDs first, then WHERE id IN (...) in one query. Or use joins. Never foreach → DB query.

03

Never block HTTP on heavy async work

Complaint created → return complaint ID immediately → assign technician in BullMQ worker. Never make the user wait for the assignment to complete. Same as Uber's "searching..." response.

04

Never store secrets in code or git

One leaked .env in a public repo = compromised production. .env.local gitignored always. Secrets in Vercel env vars or Vault. No exceptions.

05

Never add NOT NULL column without a default on live table

Table lock. Downtime. Add nullable first, backfill, add constraint. Three deploys for one schema change. Zero downtime.

06

Never skip the rollback plan

Before every deploy: write down exactly how to roll back. kubectl rollout undo / Vercel promote previous. If you can't answer "how do I revert this in 3 minutes?" — don't deploy.

07

Never build without written requirement confirmation

Sunil asks verbally → build it verbally → Sunil says that's not what I meant. Get it in writing. WhatsApp message counts. Protect yourself and protect the product.

08

Never hard delete operational data

Soft deletes everywhere — deleted_at timestamp. Complaint "deleted" by admin? Still in DB, still in audit trail. Legal, compliance, and debugging all thank you later.

09

Never hit primary DB on read-heavy endpoints

Dashboard, lists, reports — all hit Redis cache first, then read replica. Primary reserved for writes only. This single rule is responsible for half of Uber's read performance.

10

Never deploy on Friday after 4pm

Unwritten rule at every company studied. Bugs found Friday evening sit until Monday. Deploy Monday–Thursday, before 3pm. Enough time to catch and fix before end of day.

Architecture pattern: Monolith vs Microservices

Start with a monolith. Split only when a specific service needs independent scaling or its own deployment cycle.

Uber, Amazon, and Swiggy all started as monoliths. Every system that is microservices-first from day one is over-engineered. The team that tells you to go microservices on day 1 has never operated one at 3am.
